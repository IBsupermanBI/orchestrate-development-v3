# Orchestrate Development V3

Самостоятельный экспериментальный скилл Codex: Luna Max управляет задачей, Astra Low реализует результат, Sol Medium проводит внутреннее ревью, Luna XHigh выполняет исправления и финальную валидацию.

## Требования

Python 3.11+ без внешних библиотек; Codex с нативными субагентами и точным выбором модели/effort или профиля. Доступ к моделям из таблицы ниже обязателен: автоматической подмены нет. Git и аутентифицированный Codex CLI нужны только необязательному Spark-адаптеру.

## Установка

```sh
git clone https://github.com/IBsupermanBI/orchestrate-development-v3.git
cd orchestrate-development-v3
python install.py --project /path/to/project
python install.py --project /path/to/project --apply
```

На Windows используйте, например, `C:/Projects/my-project`; на macOS/Linux — `python3`, если нужно. Первый вызов показывает план без записи. Устанавливаются только файлы manifest: скилл в `.agents/skills/orchestrate-development-v3/`, пять профилей в `.codex/agents/`. Git, кеши, тесты и локальные настройки не копируются.

При конфликте проверьте план и используйте `--apply --force`: старые файлы сохраняются в `.backups/` рядом с обновляемыми файлами. Чужие файлы не удаляются. Повторная установка одинакового пакета ничего не меняет.

Пользовательская установка: `python install.py --user`, затем `python install.py --user --apply`. Корень — `CODEX_HOME` или `~/.codex`; переопределение: `--user --home /path/to/codex-home`.

## Запуск

Выберите основную модель `gpt-5.6-luna` / `max`, затем:

```text
Используй $orchestrate-development-v3 для реализации этапа.
План: <путь или требования>.
Результат и критерии приёмки: <описание>.
```

| Роль | Модель / effort | Профиль |
| --- | --- | --- |
| Владелец процесса | gpt-5.6-luna / max | основная задача |
| Реализация | gpt-6-astra / low | astra-low-worker |
| Исправление | gpt-5.6-luna / xhigh | luna-xhigh-worker |
| Узкая проверка | gpt-5.6-terra / high | terra-high-gate |
| Ревью | gpt-5.6-sol / medium | v3-sol-medium-reviewer |
| Финальная валидация | gpt-5.6-luna / xhigh | v3-luna-xhigh-validator |

Наличие TOML не доказывает его применение. Если среда не выбирает профиль, передаются точные модель, effort и инструкции роли. Свежие ревьюеры не получают историю родителя. Наблюдаемые параметры сверяются, когда платформа их раскрывает.

## Инструкции проекта

Архитектура, контракты, обязательные проверки и разрешения остаются в AGENTS.md проекта. Распределение агентов и механизм ревью принадлежат скиллу. При требовании внешних Loop Review добавьте [согласующий фрагмент](docs/AGENTS.integration.md). Эквивалентное существующее исключение дублировать не нужно. Установщик не редактирует AGENTS.md, config.toml или hooks.json.

## Зависимости

Loop Review не входит в пакет и не вызывается оркестратором. Телеметрия и защита расходов — отдельные необязательные инструменты. Orchestration guard отключён. Коммит и публикация результата требуют соответствующего разрешения.

Опциональный Spark-адаптер и его вспомогательные модули включены; см. [контракт](references/SPARK_ADAPTER.md). Доступность Spark проверяется на конкретной машине, при недоступности используется Luna.

## Гипотеза: меньше координации, больше готового результата

Мы строим этот скилл вокруг простой идеи: **экономить на полном пути до принятого результата, а не на каждом отдельном вызове модели**. Более дешёвый вызов не обязательно означает более дешёвую задачу, если после него нужны многочисленные уточнения, исправления и повторные проверки.

**Luna Max — владелец процесса.** Наша гипотеза: Luna с высоким effort достаточно хорошо удерживает требования, разбивает этап на согласованные части, распределяет границы изменений и сопоставляет результат с критериями приёмки. Мы оставляем ей управление и решения о следующем шаге, а существенную реализацию передаём Astra. Это должно позволить не расходовать ресурсы основной модели реализации на постоянную координационную переписку. Выбор Luna Max — проектное предположение, а не утверждение о гарантированном превосходстве этой комбинации.

**Astra Low — результат с первого промпта.** Под этим мы понимаем один содержательный пакет задачи: желаемый результат, связанные спецификации, границы, важные контракты и критерии готовности. Получив его, Astra сама изучает код, составляет и поддерживает опорный план, выбирает содержательные проверки, реализует, тестирует и исправляет локальные ошибки. Это не обещание безошибочного кода с одного ответа: внутри запуска могут быть несколько шагов и итераций. Цель — получить завершённый результат без постоянного управления каждым действием со стороны родителя. Предполагаем, что возможностей Astra на Low для этого часто достаточно; автоматически повышать effort скилл не будет.

Ожидаемая экономия возникает за счёт нескольких решений:

- **Крупные, но ограниченные задачи вместо множества мелких поручений.** Меньше повторной загрузки контекста, запусков и сообщений о статусе.
- **Самостоятельность исполнителя.** Опорный план помогает удерживать цель; родитель задаёт результат и границы, а не диктует каждый шаг реализации.
- **Тесты по риску.** Проверяем наблюдаемое поведение и реальные регрессии, не требуя теста каждой мелкой функции или обязательного test-first для обычной работы.
- **Ревью на осмысленных границах.** Sol Medium подключается по риску и обязательным этапам; после каждой подзадачи не запускается новый полный цикл. Гипотеза — после хорошей реализации Astra часто достаточно короткой содержательной проверки, но найденные баги всё равно требуют исправления.
- **Разделение исправлений и валидации.** Luna XHigh получает ограниченный ремонт или финальную проверку; большие наборы тестов не дублируются разными агентами без причины.
- **Компактные возвраты.** Родитель получает результат, свидетельства проверки и существенные риски вместо полного журнала работы исполнителя.

Если гипотеза верна, уменьшатся повторные проходы, расход токенов и лимитов на координацию, а время до принятого результата сократится без потери необходимой проверки качества. Если Astra приходится часто перенаправлять, Luna теряет существенный контекст или после приёмки обнаруживаются пропущенные дефекты, ожидаемая экономия может не возникнуть. **Подтверждённых процентов ускорения и экономии мы не заявляем.**

Проверять стоит на сопоставимых задачах: время до приёмки, доступный расход по моделям, количество возвратов на исправление и повторных проверок, а также дефекты, обнаруженные после завершения. Токены — только часть картины: они не равны списанию лимитов, а меньший расход не компенсирует худший результат. Для сбора доступных измерений ниже предлагается необязательная телеметрия. Она поможет собрать факты; вывод о том, работает ли гипотеза в вашем проекте, остаётся за вами.

## Необязательно: таймшеты и телеметрия

[Пакет телеметрии](optional/telemetry/README.md) сохраняет локально время работы, доступные токены, модели и роли агентов. Он полезен для сравнения расходов на реализацию, ревью и исправления, а также для отчётов JSON/CSV/Markdown. Основной скилл работает без него.

Нужен Node.js 22+ в PATH. Из корня репозитория:

```sh
node optional/telemetry/install.cjs
node optional/telemetry/install.cjs --apply
```

Первый вызов показывает план. Второй устанавливает сборщик глобально для всех проектов, сохраняя чужие hooks. Затем проверьте и доверьте определения в `/hooks` приложения Codex. Профили, AGENTS.md и защитные guards не изменяются.

Данные остаются на машине в `<Codex home>/timesheets/events-YYYY-MM.jsonl`. По умолчанию сохраняются короткие очищенные выдержки запросов и ответов; отключение — `CODEX_TIMESHEET_CAPTURE_TEXT=0` в окружении Codex до запуска. При ошибке сбора работа агента продолжается. Подробности, ограничения метрик, отчёты и отключение — в [README телеметрии](optional/telemetry/README.md).

## Состав и проверка

- [SKILL.md](SKILL.md) — инструкции workflow.
- [USER_GUIDE.md](USER_GUIDE.md) — порядок работы.
- `assets/project/.codex/agents/` — профили.
- `references/` — контракты ревью, валидации и Spark.
- `install.py`, `install-manifest.json` — автономная установка.
- `tests/` — проверки пакета без платных модельных вызовов.

```sh
python -m unittest discover -s tests -v
```

Тесты пакета не доказывают качество модельных решений или доступность моделей на аккаунте. Экспериментальный v3 устанавливается рядом с v2, не заменяя его.
